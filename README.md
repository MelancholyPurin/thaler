# thaler

A local-first personal finance planner. One Go binary, one SQLite file, no server, no bank sync.

- Double-entry ledger (accounts, transactions, postings), amounts stored as integer minor units
- Multi-currency: base currency EUR by default, switchable to USD, MXN or any other code
- Idempotent import of bank exports, with rule-based categorisation: CSV (built in for **Hamburger Sparkasse**, profiles of your own for other banks), OFX and QIF
- Run `thaler` for the interactive terminal UI (lazygit-style panels); every operation is also available as a `thaler cli …` subcommand, so it is scriptable (cron, shell)

> **Status: early, single-user.** It works locally and has tests, and the Sparkasse import profile has been tried on
> a real bank export, but there is no multi-user mode or server (see the [roadmap](#roadmap)).

## Install

Thaler runs in a terminal on **macOS and Linux**, Intel and ARM. It is one file and needs no C compiler or other library. Windows is not supported; the web application planned for later will run in any browser. Either download a release, or build it from source, which needs **Go 1.27 or newer**. A Homebrew package is planned (`PLT-7` in the [roadmap](ROADMAP.md)).

**A release.** Each release on the [releases page](https://github.com/melancholypurin/thaler/releases) has an archive per system (`thaler_<version>_darwin_arm64.tar.gz` for a Mac with Apple silicon, `darwin_amd64` for an Intel Mac, `linux_amd64` and `linux_arm64`) and `checksums.txt`. Check the one you downloaded, unpack it, and put `thaler` on your `PATH`:

```sh
grep thaler_0.1.0_linux_amd64.tar.gz checksums.txt | sha256sum -c      # on macOS: shasum -a 256 -c
tar -xzf thaler_0.1.0_linux_amd64.tar.gz
mkdir -p ~/.local/bin && mv thaler ~/.local/bin/                        # ~/.local/bin has to be on the PATH
thaler --version
```

The binaries are not signed or notarized. If you download one in a browser on a Mac, macOS refuses to open it the first time; `xattr -d com.apple.quarantine thaler` clears that (a download with `curl` is not marked at all).

**From source.** The same steps for Go and Thaler, in two parts:

**1. Get Go.** On macOS, `brew install go`. On Linux, follow [go.dev/doc/install](https://go.dev/doc/install): the distribution's own package is often older than 1.27. `go version` says which one you have.

**2. Install Thaler.** Straight from GitHub:

```sh
go install github.com/melancholypurin/thaler/cmd/thaler@latest
```

or from a clone, which leaves `./thaler` and gives it its version from git:

```sh
git clone https://github.com/melancholypurin/thaler
cd thaler
make build
```

`go install` puts `thaler` in `$(go env GOPATH)/bin` (`~/go/bin` unless you changed it). If the shell then says `thaler: command not found`, add that folder to the `PATH` in `~/.zshrc` (macOS) or `~/.bashrc` (Linux), and open a new terminal:

```sh
export PATH="$PATH:$(go env GOPATH)/bin"
```

**3. Check it.** `thaler --version` prints the version, and `thaler` opens the interface. The database and the config are in the same folders on both systems (see below).

## Quick start

```sh
thaler cli account add Assets:Sparkasse --currency EUR
thaler cli import --account Assets:Sparkasse --dry-run export.csv   # preview, writes nothing
thaler cli import --account Assets:Sparkasse export.csv
thaler cli balance
thaler cli budget set Expenses:Groceries 400   # a monthly target
thaler cli budget                              # this month against its targets
thaler cli list -a Expenses:Uncategorized

thaler                         # no arguments: the interactive UI
thaler --version               # which build this is
```

`thaler --version` prints the version the binary was built with. `make build` sets it from git (the nearest tag, else the commit, with `-dirty` when files changed); a plain `go build` or `go install` uses the version Go recorded, and `dev` when it recorded none. From a clone, run the commands as `./thaler`.

For development, `make` lists the shortcuts: `make test`, `make lint` (gofmt and golangci-lint with the pinned version and `.golangci.yml`; the same checks as CI, and the first run builds the linter, about a minute), `make tidy-check` (fails if `go.mod` or `go.sum` need a `go mod tidy`), `make check` (lint, tidy-check and the tests, in a random order: a failure prints the seed to repeat it with `-shuffle=SEED`), `make test-race` (the tests with the race detector), `make fuzz` (feeds the amount, import and config parsers inputs it makes up, `FUZZTIME` each, default a minute, checking that what they accept is read right and nothing panics; an input that fails is kept in the package's `testdata/fuzz` and from then on runs with the tests), `make vuln` (govulncheck against the dependencies and the standard library; needs the network), `make check-coverage` (per-package and total test coverage) `make build` (which also sets the version), `make smoke` (builds the binary and runs it through a backup, a restore, the interface and more on throwaway databases; `FROM=<tag>` also checks that a database of that release opens in this build) and `make release-check` (checks `.goreleaser.yaml` and builds the macOS and Linux archives into `dist/` without publishing; the first run builds the pinned GoReleaser, about a minute) and `make release-notes` (the release notes of the commits in a range, grouped by epic from the `[ID]` in their titles; see the roadmap's release train). CI first looks at which files a change touches (`.github/scripts/changed-paths.sh`, shared through the reusable workflow `changes.yml`). If only documentation and similar files changed (Markdown, `LICENSE`, `.gitignore`, `docs/`, `dependabot.yml`) the Go checks are skipped; any other file, including everything that is compiled in or configures the build, runs them. Otherwise it runs lint and the `go.mod` check, the tests, and the race detector as three parallel jobs. A last job, `Report Result`, passes when all three passed, or when all three were rightly skipped, and fails in every other case (require that one in branch protection, so jobs can change without touching the settings). `make test-scripts` tests the filter itself. Besides those it runs govulncheck on every push and on every pull request that is not documentation only, and once a week, since advisories appear without any change here. Dependabot opens one weekly pull request for routine Go dependency updates and one for the GitHub Actions; the pinned golangci-lint and govulncheck versions in the `Makefile` are not covered by it and are bumped by hand.

Export your transactions from Sparkasse online banking as CSV, choosing the **CSV-CAMT** format (the CSV-MT940 variant uses the same column names that thaler reads).

**OFX and QIF.** A bank that offers an OFX statement (also called QFX, for Quicken) or a QIF file needs no profile: the built-in profiles `ofx` and `qif` read them, and `auto` recognises them from their first lines. From an OFX statement each transaction is a row with its booking day, its amount in the currency the statement names, the name of the other side, the memo and the type of the transaction (`POS`, `DEBIT`, which the rules see like a booking text); versions 1 and 2 both work, and a file with the statements of several accounts is refused, since an import goes into one account. A QIF file of a bank, cash or credit card account gives the date, the amount, the payee, the memo and the number (`N`), in the currency of the account; the category it may name is left to your rules, and a file of an investment account is refused. A QIF date has no fixed order, so the first order that reads *every* date of the file is used, the European ones before Quicken's American `10/4'26`: a file whose days are all 12 or less could be either, so if your bank writes `DD/MM/YY`, add a profile with `format = "qif"` and its `date_formats` (see `config.example.toml`), which `auto` then prefers.

**How a file is read.** The character between the columns and the encoding are found from the file, not assumed. The delimiter is whichever of `;`, `,`, tab and `|` splits the header into the columns the profile needs (when none does, the one that splits it most, so that the error shows the header sensibly). The encoding is UTF-8, UTF-16 (with a byte order mark, or recognised by its zero bytes; what a spreadsheet saves as "Unicode text") or, for anything else, Windows-1252, which German banks still use. So an export that a spreadsheet opened and saved again with commas, or as UTF-16 with tabs, still imports with the `sparkasse` profile and is still recognised by `auto`. `thaler cli import --dry-run` says how the file was read. A profile of yours can fix either: `delimiter = ";"`, `encoding = "utf-8"` (or `"utf-16"`, `"utf-16le"`, `"utf-16be"`, `"windows-1252"`); both default to `"auto"`.

Data lives in `~/.local/share/thaler/thaler.db`, config in `~/.config/thaler/config.toml`. Override with `--db` / `--config`, or `THALER_DB`, `XDG_DATA_HOME`, `XDG_CONFIG_HOME`.

Your financial data never belongs in this repository: `.gitignore` excludes databases, CSV exports (except the invented test fixture) and `config.toml`.

## Categorising: `config.toml`

In the interface, press `C` on any screen to open the config in your editor (`$VISUAL`, else `$EDITOR`, else `nano` or `vi`; with a graphical editor use its wait flag, e.g. `EDITOR="code --wait"`). If there is no file yet it is created from `config.example.toml` with every sample switched off. When the editor closes, Thaler re-reads the file and tells you if it has a mistake. Without the interface, copy `config.example.toml` to `~/.config/thaler/config.toml` yourself. Add rules like this:

```toml
[[rule]]
contains = "REWE"
category = "Expenses:Groceries"
```

The first matching rule wins. Anything unmatched lands in `Expenses:Uncategorized` / `Income:Uncategorized`. Rules run at import time, and again on demand: after editing your rules, `thaler cli recategorize --dry-run` previews and `thaler cli recategorize` applies them to everything still uncategorized. Transactions you categorised yourself are never touched.

**Language.** Thaler speaks English, Spanish (`es`) and German (`de`). `language = "de"` in `config.toml` chooses (in the interface, `ctrl+l` opens a list of the languages: the screen changes at once, with no restart, and Thaler writes `language = "…"` into `config.toml` for you, changing only that line and leaving your comments and rules as they are; if the file cannot be written the language still changes until you quit, and the status line says so); without it the environment decides (`LC_ALL`, `LC_MESSAGES`, then `LANG`, as in `de_DE.UTF-8`), and a language Thaler does not speak is English. In the interface, amounts and dates are written the way the language writes them: `1,234.56` in English, `1.234,56` in German and Spanish, and dates as `2026-10-01` in English (ISO, which cannot be read as month first or day first), `01.10.2026` in German and `01/10/2026` in Spanish. A date you type is read in that format as well as in ISO and `DD.MM.YYYY`, so `01/10/2026` is understood in Spanish and refused in English as ambiguous; an amount is read as before, either way (`12.50` or `12,50`), and a value such as `1,234` is refused as ambiguous. `thaler cli` is English whatever the language setting, and prints amounts and dates in the plain form (`1234.56`, `2026-10-01`), so that scripts do not change with the language of the machine; it reads `YYYY-MM-DD` and `DD.MM.YYYY`, and refuses a slash date as ambiguous. Every screen and popup fits a terminal of 80 columns by 24 rows in all three languages, and a test draws about seventy of them in each language to prove it: a long text wraps onto the next line, the bottom bar leaves out the least useful key hints when the line is full (`?` always lists them all), a long status drops its last parts, and the `?` help scrolls with `↑`/`↓` when it is taller than the screen. Counts follow the language too (`1 backup`, `2 backups`; `1 Backup`, `2 Backups`). The names Thaler gives accounts itself are written in the language where you read them in the interface: the types (`Assets:Bank` is `Vermögen:Bank` in German and `Activos:Bank` in Spanish) and the accounts it makes (`Expenses:Uncategorized` is `Ausgaben:Ohne Kategorie`); the names you chose are left as they are. They are stored in English and that is what you type, what `thaler cli` prints and what a rule in `config.toml` names, so nothing changes in your data or your scripts when the language does. Errors are looked up in the same catalog, by the stable code the service gives them (`account_not_found`, `transfer_same_account`, …), so they follow the language in the interface (the command line shows them in English), whether they come from the ledger, the service, the importer or the config file (an error that wraps another, such as a file that cannot be read, is translated and then shows the system's own words after it). Everything `thaler cli` prints (help, flags, messages, errors) is English only, on purpose. All the text of the interface (every label, hint, popup, status line and the `?` help) is in the message catalog and translated into Spanish and German; a message that a language lacks is shown in English. The Spanish has been read through and checked in full; the German has been read too and is good enough to use, but its wording may still change in a later release. Words are chosen to be short where the interface cuts a label (a payee is `Destinatario` in Spanish, a description `Notiz` in German). `make i18n-check` (part of `make test` and of CI) fails when a message is missing from a language marked `Complete` in `internal/i18n`, when a translation is left over from a message that is gone or changes its arguments, when a message is not used by the code, or when the code asks for one that does not exist. For developers, `language = "pseudo"` shows every message accented and 40% longer inside brackets (`[Ñö áççöúñtš ýét. ~~~]`), to find text that does not fit before a translator does; it is not offered as a language. Translators: `make i18n-todo LOCALE=es` prints what a language still lacks as JSON to merge into `internal/i18n/locales/es.json` (the English to translate is printed on standard error).

**Colours.** The interface uses four colours (green for what is selected and the focus, orange for a warning, red for an error, grey for what is secondary) and picks the pair that suits the terminal: it asks the terminal whether its background is light or dark. Where the terminal does not answer (some multiplexers, a session over ssh) it can guess wrong and draw pale text on a pale background. `theme = "dark"` or `theme = "light"` in `config.toml` then fixes it, and `theme = "auto"` (the default) follows the terminal. In the interface `ctrl+t` opens the list: moving through it tries each theme on the screen at once, `enter` keeps one and writes `theme = "…"` into `config.toml` (changing only that line, as the language does; if the file cannot be written the theme still changes until you quit, and the status line says so), and `esc` puts back the one in use. The sample line of four dots shows the colours. A theme only changes colours: the selection is reverse video and the other emphasis is bold, so nothing depends on colour alone, and with the `NO_COLOR` environment variable set the interface draws without colours at all. An unknown theme in the file is refused with a message that lists the ones there are.

**Features that are not finished.** A story that is merged before it is done stays off until `config.toml` switches it on, in a `[features]` table (`some_feature = true`). That keeps an unfinished story from holding up a release. A name that does not exist is refused, and the error lists the ones that do. Nothing is behind a flag in this version.

Re-importing the same or an overlapping export is safe: every row gets a stable hash (account, date, amount, counterparty, IBAN, purpose, booking text). Two truly identical bookings on one day are numbered, so they are kept as two. Rows the bank marks *Umsatz vorgemerkt* (pending) are ignored until booked.

**Logging an expense** is built to take a few keystrokes. Press `a`:

```
amount ⏎   payee ⏎   category ⏎        e.g.   8.40 ⏎  rew ⏎  ⏎
```

- The **account** is the one selected in the Accounts panel. With "All accounts" selected it is the account you used last (in this session, or else the most recent transaction in the database). Amounts are in that account's currency, so there is no currency to type.
- **Amount:** `12.50` is an expense, `+2450` is income.
- **Payee** is the title the transaction has in the list (rename it later with `r`): typing the start of a known payee highlights it, and Enter completes it. `↑` drops the suggestion if you meant something new.
- **Category:** the category that payee went to last time is offered first (marked "same payee"), then the category of payees that look like it (marked "similar payee"), then categories of the right kind by how often you use them. Type to filter, or type a full new name such as `Expenses:Gifts`. The last entry, "decide later", books it as uncategorized.
- **Description** is optional and comes after the date (`tab` from there; it is not in the way of the quick path above). Use it for a note about what the transaction was for. It is shown beside the transaction, searched by `/`, and for an imported row it starts out as the bank's purpose text, which you can edit or clear.
- **Date** defaults to today: `y` is yesterday, `-2` is two days ago, or type `2026-10-20` / `20.10.2026`. Mistakes are reported in the form and nothing is written.

**Moving around the form.** The line under the form says what `Enter` does on the field you are on. Adding is built to be quick, so there `Enter` on the *category* saves; everywhere else `Enter` moves on, and when you edit it walks through every field and saves on the *description*, so all of them can be reached with `Enter` alone. To go back, press `↑` (on the amount, date and description, `↑`/`↓` move between fields; in the payee and category lists `↑` first moves through the suggestions and then goes back) or `shift+tab`; `tab` goes forward. `ctrl+s` saves from anywhere and `esc` cancels.

**Creating an account** needs no command line. Press `n`, type a name (`Sparkasse` becomes `Assets:Sparkasse`), pick Assets or Liabilities, and confirm the currency (it starts as your base currency). If you already know what the account holds, fill in **Balance** and **As of**; leave them empty to start from nothing.

**Moving money between your accounts.** Press `x`. Type the amount; the accounts start as the selected one and another with the same currency, and `tab` then `◂ ▸` changes them (choosing the other field's account swaps the two). When the accounts hold different currencies a *Received* field appears: type what actually arrived, which fixes the exchange rate you got (`1 EUR = 1.0850 USD` is shown as you type). A transfer is booked as two linked transactions, one on each account, like the two lines on your bank statements: they go to `Equity:Transfers` (or `Equity:Conversions` across currencies), so a transfer is neither income nor spending. **`e` on either half edits the transfer as one thing**: the same popup opens, titled with both numbers and filled in, and the amount, what arrived, the date and the two accounts change on both halves together; they keep their numbers and stay a transfer. When the bank booked the two halves on different days, the half that arrives keeps its own day unless you change the date (the popup says which day that is). A payee Thaler wrote follows a new account; one from the bank stays. **`d` on either half deletes both**, after showing both; marked transactions that include a half take the other half along. `z` takes back a new transfer, a change or a delete, and a deleted transfer comes back linked. **Linking two you already have.** Money you moved yourself often arrives as two ordinary transactions, entered by hand or imported before the other account was. `l` on one of them lists what could be its other half: transactions on another of your accounts that move the opposite amount and are not a transfer already, the nearest in date first; `enter` links the one chosen, and both are booked to `Equity:Transfers` and marked `⇄`, so the move is neither spending nor income. To link two that the list does not offer (across currencies, where the amounts differ), mark both with `space` and press `l`: within one currency they must move the same amount, one out and one in, and across currencies they go to `Equity:Conversions`. `l` on a half of a transfer unlinks the two, which then wait in Uncategorized. `z` takes back a link or an unlink. On the command line: `thaler cli transfer link A B` and `transfer unlink ID`. `r` still opens the ordinary form on one half, to rename it or give it a note. Recategorizing one half with `c`, or changing its amount there, still dissolves the pair. On the command line: `thaler cli transfer --from A --to B --amount N [--to-amount M]`. **Changing or deleting a transfer as a whole:** `thaler cli transfer edit ID` changes both halves together, given either half's number: only the flags you give change (`--from`, `--to`, `--amount`, `--to-amount`, `--date` for both halves, `--in-date` for the half that arrives, `--memo` for both descriptions), and the halves keep their numbers and stay a transfer. A payee Thaler wrote (`Transfer to Savings`) follows a new account; a payee and a text from the bank stay. `thaler cli transfer delete ID` lists both halves, and with `--yes` deletes both, or neither when one is on a closed account. Deleting one half alone and taking it back with `z` links it to the other again. Importing the bank statements later takes the two halves over (see below) instead of adding them again.

**Renaming and closing accounts.** `thaler cli account rename Assets:Bank Assets:Sparkasse` gives one of your own accounts (Assets or Liabilities) a new name; the new name keeps the type and must not be taken, and everything that belongs to the account (transactions, schedules, its minimum balance) goes on belonging to it, since each of those refers to the account and not to its name. `thaler cli account close Assets:Old` sets an account aside once you no longer use it: it has to hold nothing, in any currency (move what is in it to another account first), and no schedule may book to it, so closing never hides money or leaves a schedule that cannot be confirmed; a refusal says which. A closed account keeps its history: its transactions stay, a balance report as of a day it was in use still counts what it held, and the net worth of those months does not change. It is marked `closed` in `account list`, left out of the forecast, and takes nothing new: no transaction, transfer, import, opening balance or schedule can book to it, and its transactions cannot be edited or deleted (their category can still be changed), until `thaler cli account reopen` takes it back. `account list --json` gives each account a `closed` field. In the interface the same is done in the Accounts panel (`2`): `r` asks for the new name of the selected account (you type what follows the type, `Sparkasse` for `Assets:Sparkasse`; a name that is taken, another type or not a name is said in the popup and nothing changes), and `c` closes it, saying why when it holds money or a schedule books to it. A closed account disappears from the panel, the forms and the transfer list; `v` shows the closed accounts after the others, dimmed and marked `closed`, with their transactions as their history, and `c` on one of them reopens it. A transaction of a closed account cannot be edited or deleted (the status line says to reopen the account), but its category can be changed with `c` as before. `z` takes back a rename, a close or a reopen.

**Filtering and sorting the transactions.** The Ledger already narrows its list by the account selected in the Accounts panel (`2`), by the month on show (`[` `]`, `t`, `T`), by `u` (only what needs a category) and by the search (`/`). `f` adds more: a minimum and a maximum amount, a first and a last date, part of a category name, and the order. The amount is the size of the transaction on your own account whichever way the money went (a spending of 12.00 and an income of 12.00 are both 12.00), the ends are in, and in a ledger with several currencies each transaction is compared in its own (15 means 15 dollars for a dollar account and 15 euros for a euro one). A date is written as the language writes it, or `YYYY-MM-DD`, and either end may be left out: dates take the place of the month on show for the Ledger (the bar at the top says `2026-09-01 – 2026-09-30`, `from 2026-10-04` or `until 2026-09-16`; the other screens keep the month). The category is matched like the search, by letters in order: `groc` finds `Expenses:Groceries`, and a transaction counts when any of its categories does. The order is chosen in the last field with `←` `→`: date (newest first, as before, or oldest first), amount (largest or smallest first), payee or category, A to Z. Everything works together with the account, the month, `u` and the search. The Transactions panel says `filtered` and `sorted` in its title, and the status line how many transactions match. A problem (an amount that is not a number, a minimum above the maximum, dates the wrong way round) is said in the popup and nothing changes; `ctrl+x` there clears the filter, and so does `esc` in the list (the order stays, as it is a preference). The account is filtered by selecting it in the Accounts panel, as before.

**Several transactions at once.** On the Transactions panel `space` marks the one under the cursor (a `✓` in place of its usual sign, and the panel title says how many are marked) and moves down, so a run of them is `space space space`; `ctrl+a` marks everything on show, and again lets go of it all. `c` then asks for one category for all the marked transactions, `enter` puts them there, and `d` lists what is about to go (the first few, and how many more) and asks before deleting them. Both are all or nothing: if one of them cannot be changed (a transfer or a split transaction cannot be recategorized here; a transaction on a closed account cannot be deleted) nothing is, and the status line says why. `z` undoes the whole group in one step, with the transactions back under their old numbers. A mark is only ever on a transaction you can see: a search, a filter, another account or another month hides it and the mark goes with it, so what is categorized or deleted is always what is on screen. `esc` lets go of the marks (before it clears the search or the filter). A rule is made from one payee, so the category popup of several transactions has no rule field; with one transaction marked, `c` and `d` act on it wherever the cursor is, and the popup is the usual one.

**Splitting a transaction.** One payment is often several things: a shop bill that is groceries and household goods, a salary that is pay and a bonus. `s` on a transaction opens the split popup (so does `ctrl+o` in the form that adds or edits one, which carries over what you typed, so a new split starts with `a`). It has the account, the amount (with a `+` for income), the payee, the date and the description, as the form does, and under them the lines, each a category and its share of the amount, written without a sign. Type a few letters of a category and `↑` `↓` choose, as in the category list, or a full new name such as `Expenses:Gifts`. One line may be left without an amount and takes what the others leave; the popup says what is left to give out, or by how much the lines are over. `tab` goes through the fields, `ctrl+n` adds a line below the one you are on, `ctrl+x` removes it, `ctrl+s` saves. Saving is refused until the lines add up to the amount, and nothing is written before: the transaction is one booking on your account with a posting for each category, so every report and the budget count each category's share. A split shows as `»` in the list; `e` or `r` on one opens the same popup, and `z` takes the change back. A transaction with one line is an ordinary transaction again. Only a transaction on your own account with income or expense categories can be split: a transfer between your accounts cannot, and a closed account's transaction cannot be edited. A split cannot be categorized with `c` (that is for one category), nor can the marked transactions that include one. Thaler itself checks every split it writes, from the popup or from `thaler cli split`: one account of yours, Income or Expenses categories each taking a share in the currency of the account, and shares that add up to the amount.

**Matching your bank's balance.** An import only brings in movements, so an account's balance is wrong until Thaler knows where it started. Select the account and press `b`, then type what your bank shows on a given day. Thaler books the difference as one *opening balance* transaction against `Equity:Opening`, dated the day before the account's first transaction, so the whole history adds up. Press `b` again after the next import and it corrects that same transaction instead of adding another. For a credit card or loan, type the amount you owe (a card showing 500.00 owed is `500`). `z` takes the change back. On the command line: `thaler cli account balance ACCOUNT AMOUNT --as-of DATE`.

**Importing a bank export** works from the interface too. Press `i`:

- **File:** the bank exports in `~/Downloads` (CSV, OFX and QIF files, by their `.csv`, `.ofx`, `.qfx` and `.qif` names) are listed, newest first, so the export you just downloaded is already highlighted. Type a few letters to narrow the list, or paste or drag a file path into the field. Type or drop a *folder* path (say `~/Desktop`) to list that folder's exports instead. To list a different folder every time, set `import_dir = "~/Documents/bank-exports"` in `config.toml`.
- **Account** (default: the one selected in the Accounts panel) and **profile** are changed with `tab` and `←` `→`. The profile starts as **auto**: Thaler reads the header of the file you have highlighted (or typed) and picks the profile whose columns it has, shown as `auto: sparkasse` and again in the review (`profile sparkasse`), so a file from another bank is read with your own profile for it (see `config.example.toml`) with nothing chosen. A profile fits when the file has the date and amount columns it names; the one that names the most of the file's columns wins (one that lists every column of a bank's export beats one that lists two), and between equals yours from `config.toml`, in the order written, come before the built-in ones. When none fits, `enter` says so instead of guessing, and `←` `→` choose a profile by hand, which is then used as it is, even if the file does not look like it, and is the one offered the next time (`auto` stays `auto`). `thaler cli import` finds the profile the same way unless `--profile` names one.
- `enter` shows a **review** and writes nothing: how many rows are new, how many were imported before, how many no rule matched, and each row with the category the rules chose. A second `enter` imports. If some rows cannot be read, they are listed and `y` imports the rest.
- **`c` changes the category of the row under the cursor** before anything is written, in the same list as everywhere else (type to narrow it, or a full name such as `Expenses:Gifts` to make a new one; `enter` chooses, `esc` leaves it as it was). Your choice wins over the rules and over the category of a schedule, is marked `✎` in the review, and is what the import writes; `r` goes back to what the rules chose, and reading the file again forgets every choice. The review is worked out again each time, so the counts follow: a row you categorize stops counting as uncategorized, and a row you put in `Equity:Transfers` is paired with the other half like any transfer, while one you put elsewhere is not. Choosing `Uncategorized` leaves the row for later. A row that was imported before, or that takes over an entry of yours, keeps its category (the line under the list says why). Nothing is stored for a rule: to make the choice a rule for next time, add one in `config.toml` or categorize the row with `c` after the import.
- Afterwards the account's uncategorized rows are shown, ready for `c`, and `z` takes the whole import back.
- **A new export is noticed.** While Thaler runs it looks at the import folder every few seconds, and when a bank export arrives that was not there before (the export you have just downloaded, or one saved again under the same name) the bottom bar says `new export umsaetze.csv · i imports it`, or how many have arrived. The file is already highlighted when you press `i`, which also takes the message away; with the file list open it is added to the list at once. What was in the folder when Thaler started, or when `import_dir` changed, is not new, and a message appears only for files seen arriving. Only the names, sizes and times of the exports are read, never what is in them, and nothing is imported until you say so. `watch_import_dir = false` in `config.toml` switches it off.
- **`I` lists the imports you made**, newest first: when, the account and the file, and under the list what the one under the cursor did (rows added, entries of yours it matched, transfers it paired, dates of schedules it answered, the profile). `enter` takes it back as a whole, after saying what will go. This works for any import, not only the last one, and also for one made with `thaler cli import`. It deletes the transactions the import added, makes the entries of yours it took over hand-entered again, puts the other halves of the transfers it paired back to the category they had (one you have changed since stays as you left it), and makes a date of a schedule it answered due again. What you changed on the deleted transactions since (a category, a note) goes with them, and `z` does not bring them back: import the file again for that. An import whose account has been closed is refused. A record keeps the name of the file, not the folder, and the profile; imports made before this list existed are not in it.

**Entries you made by hand are not added twice.** If you log expenses yourself and later import the statement, each bank row is checked against what you typed: the same account, exactly the same amount, dated within three days, an ordinary entry (one account, one category) that has not been matched to a bank row yet. When one is found, the row *takes over* that entry. Nothing is added; the entry just remembers which bank row it is, so importing the file again recognises it. Your payee, date and category stay as you typed them, whatever your rules would have chosen. The review shows these rows as `↔ #12 REWE` before anything is written, each entry is taken over at most once (the closest date first), and `z` lets go of it again. This works for the two halves of a transfer you entered with `x`, too. Entries that are splits, that move between two of your accounts in one transaction, or are an opening balance are never matched.

**Monthly targets.** On the Budget screen, pick a month and press `e`: a popup lists your spending categories with the target each has for that month. Move with `↑` `↓`, type an amount, and `enter` saves it; an empty amount clears the target, and `z` takes a change back. A target belongs to one month (a month keeps its own, so changing next month's leaves this one alone) and is in the base currency; the popup sets them on expense categories (an Income category can have one too, see Planned income below). For that month the Budget shows the total target and what is left of it, and under each category with a target what was spent, the target and what is left, or by how much it was passed, with the bar and the amount in red. Spending in categories with no target is listed apart, and does not take from what is left of the planned categories. `c` starts the month on show from the month before: it adds the targets the month lacks and keeps the ones it has, so nothing is overwritten, and `z` takes back exactly what it added. All time has no targets: pick a month.

**Category groups.** Categories below one another are a group: `Expenses:Housing:Rent` and `Expenses:Housing:Power` are in `Expenses:Housing`, and so are deeper ones such as `Expenses:Housing:Utilities:Water` (a group is the first level under the type; a category named like the group, `Expenses:Housing` itself, counts as one of its members once there is one below it). A group has nothing of its own to set: its target is the sum of its categories' targets, so setting, clearing and copying targets work as before and nothing is counted twice. The service adds each group up for the month (`MonthBudget.Groups`: spent, target, carried in, left, and what the categories without money set aside spent, which like the month's own figures is kept apart from what is left), and the groups together with the categories in none add up to the month's totals. `thaler cli budget` shows them in a second table under the categories, and `--json` has them as `groups`. The Budget screen shows them: in a month, each group is a row that adds up its categories, with the categories under it, and `space` folds a group so that only its row shows (see below).

**Folding a group on the Budget.** With the categories in focus (`tab`), a group is a row of its own, marked `-` while its categories are shown under it and `+` while it is folded: its name, what the group spent, a bar and the sum of its targets and what is left, as a category with a target. Its categories follow, indented, under their names without the group's (`Rent` under `Housing`), a category without a target as one line, and the one named like the group as `Housing (directly)`. A group that has a category with a target is listed with the targets, with all of its categories; one that has none is listed with the others that have no target. `space` folds the group the selection is in, or unfolds it when it is folded, `←` folds the group, or goes from a category to its group, and `→` unfolds it; a folded group is stepped over by `↑` `↓`. `enter` on a group opens the Ledger with the transactions of all of its categories (the group's name in the Transactions title), on a category with its own, as before. All time and the months without targets are grouped in the same way. Folds are kept while Thaler runs, not in `config.toml`.

**The transactions behind a number.** On the Budget, `tab` moves from the months into the categories (the same panel that shows the figures, with its own `▸` mark, scrolling when there are more than fit), `↑` `↓` choose one, and `enter` opens the Ledger with its transactions: the month on show, every account, and the category in the panel's title. It is the same list the number was added up from, so you can edit, recategorize or delete from there, and `esc` shows everything again. `tab` or `esc` goes back to the months.

**Planned income.** An Income category can have a target as well: what you plan to receive from it that month. In the target popup (`e`) the income categories follow the spending ones, marked `+`, and the field is called Planned instead of Target; `tab` does nothing there, since income has nothing to carry. On the command line it is `thaler cli budget set Income:Salary 3000 --month 2026-10`. For a month with a plan the Budget shows **Planned income** and **Unassigned**: the planned income less the targets of the spending categories, in red when the targets add up to more than the plan. Under Income each planned category shows what has come in against the plan (`of 3000.00 · 100.00 still to come`, or `400.00 above plan`); the others are listed as before. `c` copies the plans forward with the other targets. `thaler cli budget` lists them too: for a month with income planned it adds an Income table (received, planned, and to come, negative once the plan is passed) and a line "Unassigned: … (planned income … less targets …)"; without a plan the output is as before.

**Recurring transactions.** A schedule is a transaction that repeats: rent every month, a salary on the 28th, an insurance every year. The Forecast screen (`F`) lists them, the one that comes soonest first, with what each moves and when it is next due; `↑`/`↓` move through them. A date that nobody has answered yet is marked `!` and counted above the list, and a paused schedule or one that has run out says so. **`n`** makes a new one and **`e`** changes the selected one, in a popup like the other forms (`tab` and `enter` move on, `ctrl+s` saves, `esc` cancels): a name, an amount (no sign is money out, `+` money in), the account it moves on, and what it goes to, which you type and choose from the list of your categories and other accounts. Choose one of your accounts and it becomes a transfer, which asks what arrives when the two hold different currencies. Then how often (every N weeks, months or years), the first date, an optional last date and, for what is not a transfer, a tolerance in percent for bills that change. What gets booked is called by the schedule's name. **`p`** pauses the selected schedule, or resumes it, and `z` undoes any of these. A schedule with several postings can only be changed through the service, not here. **`enter`** goes through what is due, the oldest date first, one at a time (the same dates as `thaler cli schedule due`). Thaler only asks: `enter` books the date as it is, on its own day, `e` books it for the amount it really was (for a bill that changes, or when what arrived differs), `s` skips it, `↑`/`↓` look at another date and `esc` stops. After each answer the next date comes up, until none is left. A transfer is booked as the two linked transactions of `x`. `z` takes the last answer back: a booking is deleted and a skip is lifted, so the date is due again. `schedule add Rent --unit month -a Assets:Bank --amount=-900 -t Expenses:Rent --start 2026-11-28` defines one, `--every 2` makes it every second week, month or year, and a schedule that starts on the 31st falls on the last day of shorter months. **Thaler never books one by itself.** `schedule due` lists the dates up to today that are not answered yet, and each is answered with `schedule confirm ID DATE` (booked on that day, `--amount=-950` for another amount) or `schedule skip ID DATE` (nothing booked). A date answered does not come back; if you delete the transaction a confirm booked, its date is due again. **An imported bank row settles the date it belongs to:** a row on the schedule's account for exactly the schedule's amount, dated within three days of an unanswered date, answers that date (the nearest one, if two are in reach) and is booked to the schedule's category unless one of your rules picks another; the import says so (`Settled 2026-08-28 of the schedule Rent`), `--dry-run` counts them, and taking the import back (`u` in the interface) makes the date due again. A row that takes over an entry you made by hand leaves the schedule alone, so skip that date yourself. `schedule edit ID` changes only the flags you give, `schedule delete ID` removes a schedule and keeps what it booked, and `schedule` alone lists them. **Bills that change:** for the electricity, give the amount it usually is and a tolerance: `schedule add Electricity --unit month -a Assets:Bank --amount=-80 -t Expenses:Power --tolerance 25` (`edit ID --tolerance 0` makes it exact again). A bank row within 25% of 80.00, above or below, in the same direction, still settles its date, and what is booked is what the bank says. Lists show such an amount as `~-80.00 EUR`. Confirming a date by hand takes `--amount` as for any schedule, whatever the tolerance. A scheduled transfer has no tolerance. **Transfers:** a schedule can move money between your own accounts, such as a monthly saving: `schedule add Saving --unit month -a Assets:Bank --amount 200 --to Assets:Savings` (`-a` is the account it leaves, `--to` the one it arrives in; between currencies `--to-amount` says how much arrives). Confirming a date books a transfer, the two linked transactions of `thaler cli transfer`, and `--amount` and `--to-amount` change what moves for that date. A bank row of the same amount on either account settles the date and is booked to `Equity:Transfers`; the other account's row then pairs with it as usual. **Ending and pausing:** `--end DATE` (on `add` or `edit`; `--end none` takes it away) is the last day a date may fall on. `schedule pause ID` stops it proposing anything from today and `schedule resume ID` starts it again from today; the dates that fell in between are dropped, not held back, and a bank row does not settle one of them. Dates before a pause that nobody answered stay due. **Where the balances are heading:** `thaler cli forecast [--until DATE]` works out what each account would hold if every schedule were confirmed: the balance today, then each day a schedule moves it with what changes and the balance after it (90 days ahead unless `--until`). A date that came and nobody answered counts today, a skipped or confirmed one does not count, a paused or ended schedule stops, and a transfer moves both accounts, each in its own currency. Only the schedules count: a purchase you have not made yet is not in it, and neither is a transaction already booked with a date to come. Nothing is booked. On the Forecast screen **`tab`** switches from the schedules to the balances: for each asset and liability account what it holds today, then what it would hold at the end of each of the next 13 weeks (the first week ends a week from today), with what the schedules move in that week; `↑`/`↓` scroll, `tab` goes back. A balance under the account's minimum is marked `!`, and the warnings stay above. **`a`** limits the Forecast to one account, the next each time and all of them again after the last, and the title says which: its schedules (those that move it, a transfer in either of its accounts), its balances and its warning, and `enter` goes through the dates of those schedules only. A new schedule starts on that account, and one saved for another account shows them all again. **A minimum for an account:** `thaler cli account minimum Assets:Bank 500` says the account should not fall below 500.00 (`--amount=-300` for an agreed overdraft, `--clear` to take it away, no arguments to list them). `forecast` then ends with a warning for each account that would go under it, with the first day, the balance that day and the schedule that takes the most out of it; one that is under it already is said to be under today. Balances are compared at the end of a day, so a salary and a rent on the same day are taken together. An account with no minimum is never warned about, and only an Assets account can have one. On the Forecast screen **`m`** sets the minimum of an account in a popup (the Assets accounts are listed with theirs; type an amount, or leave it empty to clear it; `enter` saves, `esc` cancels, `z` undoes), and the screen says, above the schedules, which accounts would fall under theirs in the next 90 days: the first day, the balance that day and the schedule that takes the most out of it, or that the account is under its minimum already.

**Carry-over.** In the same popup, `tab` makes the category under the cursor carry what is left of it into the next month, from the month on show (that month itself starts with nothing carried in). What was left comes in as a positive amount, and what was overspent as a negative one, so overspending is paid back out of later months. A month with no target in between goes on, carrying what it spent. Nothing is stored for it: the carried amount is worked out when shown, from the targets and the spending of the months since (spending at the exchange rate of the day it was made), so editing or importing an older transaction can never leave a stale figure. The Budget shows `of 50.00 · +70.00 carried · 110.00 left` for such a category and a `Carried in` total; `z` takes the switch back.

**Transfers between your own accounts.** Import your current account and your savings account and the same transfer appears in both exports, once going out and once coming in. Counted as an expense and as income, it would inflate both on the Budget screen. So when a new row has the exact opposite amount of a transaction on another of your accounts, within three days, and neither is categorized yet, Thaler pairs them: both are booked to `Equity:Transfers` (so they are neither income nor spending), marked `⇄`, and linked to each other. The import review shows `⇄ Bank` on a paired row before anything is written, and `z` takes the pairing back with the import. It works in either order, each row is paired at most once, and a row a rule has already put in a real category (rent, say) is left alone. Add a rule with the category `Equity:Transfers` to mark a transfer whose other half has not been imported yet; the balance of `Equity:Transfers` is what is still waiting. If you recategorize or change one half, the pair is dissolved and the other half goes back to uncategorized so you notice it.

Rules and profiles are read from `config.toml` each time you press `i`, so you can edit them in another window and import again.

**Renaming and merging categories.** `K` lists every category, spending first and income marked `+`, each with its number of transactions; the cursor starts on the category of the transaction selected in the Ledger, or the one selected on the Budget. `r` (or `enter`) asks for the new name, written whole (`Expenses:Dining`) and of the same type: the category and the categories below it (`Expenses:Food:Out`) are renamed, and its transactions, targets, carry-over and schedules follow; `z` takes it back. `m` asks which other category of its kind to merge it into, then asks again before it moves all its transactions, schedules, targets (a month the other already has a target for keeps the other's) and carry-over (unless the other has one) and removes it; `z` cannot take a merge back, and a category with categories below it is refused until those are merged. Rules in `config.toml` that name the category are not changed: the status line says how many still do, so that you can edit them (`C`).

**Managing the rules.** `M` lists the rules of `config.toml` in the order they are checked (the first match wins), a text to look for in quotes and a regular expression between slashes, each with its category. `e` (or `enter`) edits the one under the cursor: the text it looks for and its category, with `tab` going from one to the other and `enter` saving; a text that is too short, an expression that does not compile or a category that is not a name is said in the popup and nothing is written. `<` and `>` move the rule one place earlier or later, since the order decides which rule wins, and `d` deletes it after asking. `z` takes back the last change, in the popup or after closing it, as long as nobody has changed the file since; Thaler never writes over a file it did not write. Only the lines of the rule that changes are rewritten: your comments, your settings and the other rules stay as they are, and a comment directly above a rule (no blank line between) moves with it; a comment on one of the rule's own lines goes when the rule is edited. A file whose rules are not written as `[[rule]]` tables one after the other (a list, a string over several lines) is refused with a message, and edited with `C` as before. The transactions a rule has already categorized are not changed by editing or deleting it, and a new order does not change them either. `a` applies the rules, as they are in the file now, to the transactions that are still uncategorized (the ones a rule categorized or you categorized by hand are never touched): it says first how many would get a category, and asks; `enter` or `y` does it and `z` puts them back, in the popup or after closing it. It is what `thaler cli recategorize` does, and it is for the rules you wrote or changed after those transactions came in.

**Making a rule while you categorize.** In the category picker, press `tab` to move to a *Rule* field. It starts with the payee; trim it to the part that matters (`REWE Markt GmbH Filiale 12` → `REWE`). As you type, the picker says how many other uncategorized transactions it would catch. `enter` then categorizes this transaction, appends the rule to `config.toml`, and categorizes the matching ones too. `z` takes the categories back in one step; the rule stays in the file (press `C` to remove it). Only the end of the file is ever written, so your comments and the order of your rules are untouched. Rules are checked top to bottom and the first match wins, so if an earlier rule already decides this payee differently the picker names that rule and refuses, instead of adding one that could never apply.

In the category picker the category you last used for the same payee comes first (marked "same payee"). Right after it (first, if that payee is new) comes the category of payees that look like it (marked "similar payee"): banks write one shop in many ways ("REWE SAGT DANKE 4711", "REWE Markt Berlin"), so Thaler compares the words of the payee, ignoring numbers, legal forms (GmbH) and booking words (Kartenzahlung), and counts a word that few of your payees have (REWE) for more than one many share (Deutsche, Berlin), so that "Deutsche Bahn" does not borrow the category of "Deutsche Bank". It is only a suggestion, put first so that `c` `enter` takes it, never applied by itself, and it is left out when nothing looks alike enough. Then come the categories of the matching kind (income for money in, expenses for money out), most used first. Type to filter, or type a full new name such as `Expenses:Gifts` to create it. Transfers and split transactions are shown but cannot be recategorized there.

**Backing up.** Press `S` to open the backup popup. It shows the database, when the last backup was made ("2026-10-22 14:00 · 3 days ago"), and how many are in the backups folder, which sits next to the database (`backups/`). `enter` writes a snapshot to the file name in the *Save to* line, which starts out as `thaler-<date>-<time>.db` in that folder. You can type any other path instead (`~` is your home folder), or just a folder, which gets the timestamped name inside it. A file that already exists is never overwritten. After writing, Thaler opens the snapshot and runs SQLite's integrity check on it; a snapshot that fails is removed and reported, so a backup that is announced is one that opens.

**A reminder to back up.** When the newest backup in the backups folder is 7 days old or older, or there is none and you have transactions, the bottom bar leads with "Last backup 9 days ago: S makes a new one" (or "No backup yet") until you make one. Set `backup_reminder_days = 14` in `config.toml` for another interval, or `0` to switch the reminder off. Only backups in the backups folder count, as in the popup; ones you wrote elsewhere, the copies in `replaced/` and `pre-migration/` do not. It is checked when Thaler starts, after a backup, after you edit the config, and (at most once a minute) on a key press, so a backup made by a script while Thaler is open ends the reminder too.

**Pruning old backups.** Backups pile up, and nothing removes one by itself. Thaler keeps the newest 10 in each of three folders: the backups you make (`backups/`), the databases that restores replaced (`backups/replaced/`) and the copies made before upgrades (`backups/pre-migration/`). When a folder holds more, the bottom bar says "3 old backups can be removed: ctrl+p". `ctrl+p` lists exactly which files would go, oldest ones, with their dates and sizes, and `enter` removes them; `esc` leaves them. "Old" is the time a file was last changed, plain and encrypted backups count together, and the newest ones always stay. Only files named like a backup (`thaler-*.db`, `thaler-*.db.age`) are ever listed, so anything else in those folders, and backups you wrote elsewhere, are never touched. Set `keep_backups = 20` in `config.toml` for another number, or `0` to keep everything and stop the offer. From a script, `thaler cli prune` lists what would go and `thaler cli prune --yes` removes it. Removing is permanent; a removed backup is not in the trash.

**Encrypting a backup.** By default a backup is a plain SQLite file, which anyone who gets hold of it can read. Press `tab` to the *Passphrase* line and type one (it shows as `•`), then `tab` to *Repeat* and type it again, so a typo cannot lock you out. The backup is then written as an [age](https://age-encryption.org) file ending in `.age`, sealed with a key derived from the passphrase by scrypt (it takes a second or two, on purpose; the popup shows a spinner and what it is doing meanwhile, and ignores keys until it is done, apart from `ctrl+c`, which quits right after). Thaler decrypts the result once before it says it is done, to be sure the passphrase it holds opens it. The unencrypted copy exists only for a moment, in a private folder next to the backup, and is deleted. **There is no way to recover a backup whose passphrase is lost.** The popup and the status line say whether a backup is encrypted, and the *Last backup* line says so for the newest one.

**A copy before every upgrade.** When a new version of Thaler has to change the structure of a database that already holds data, it first writes a checked copy to `backups/pre-migration/` next to the database, named `thaler-<time>-before-<migration>.db`, and says where it is on standard error. If the copy cannot be made, the upgrade does not happen and nothing is changed. A new database, one that is already up to date, and one written by a newer version (which is refused) get no copy. These copies are plain, not encrypted, and are kept apart from the backups you make so that they never count as your "last backup"; `ctrl+p` and `thaler cli prune` prune them (see below).

**Restoring.** `thaler cli restore FILE` replaces the database with a backup, plain or encrypted (it asks for the passphrase, or reads `--passphrase-file`). The backup is read into a new file and checked first: one that is damaged, is not a Thaler database, or was made by a newer version is refused with nothing changed. Only then is the database in place moved, never deleted, to `backups/replaced/` next to it, and the backup put in its place. Running `thaler cli restore` on the file in `backups/replaced/` undoes a restore (the command prints it). It works when the database in place is damaged or missing. A backup from an older version is upgraded, after a copy of it, the next time Thaler starts. Close every other Thaler first; the restore does not look for one.

**Restoring from the interface.** `ctrl+r` opens the restore popup. It lists the backups in the backups folder, newest first, then the databases earlier restores replaced (marked "replaced by a restore"), so a restore can be taken back from the same place. Choose one with `↑`/`↓`; for an encrypted backup `tab` to *Passphrase* and type it. `enter` asks once more, naming the file and where your current database will be kept, and a second `enter` (or `y`) restores. Nothing happens until then, and a backup that is damaged, has the wrong passphrase or is not a Thaler database is refused with the database untouched and the popup still open. After a restore the screen shows the restored data and undo starts afresh (it cannot reach back across it). A backup that is not in the folder: `thaler cli restore FILE`.

To open an encrypted backup again, `thaler cli decrypt FILE.age [DEST]` asks for the passphrase and writes a plain database (default: the file name without `.age`; an existing file is never overwritten, and a wrong passphrase leaves nothing behind). Use the result with `thaler --db DEST`. Because it is a standard age file, the `age` tool opens it too (`age -d`).

On terminals narrower than 76 columns the detail pane is hidden, and below 14 rows only the focused panel is shown.

## Multi-currency

- Every account has a currency (Assets/Liabilities) or accepts any (Income/Expenses/Equity). Amounts are never converted when stored.
- **Base currency** only affects reports: `thaler cli currency` shows it, `thaler cli currency set USD` changes it.
- **Exchange rates** are recorded by you: `thaler cli rate set USD EUR 0.92` means 1 USD = 0.92 EUR. One direction is enough; the inverse is derived, and USD → MXN is routed through any currency that has rates to both (EUR, say). Reports use the latest rate on or before the report date.
- **Budgets count each day at its own rate.** Spending and income in another currency are converted into the base currency at the latest rate on or before the day they were booked, so entering a new rate later does not move a month that is already counted; a day before the first rate of its currency takes the rate at the end of the month. A target is in the base currency, so the Budget screen and `thaler cli budget` compare it with spending in every currency, and a currency with no rate at all is named and left out.
- `thaler cli balance` shows each account in its own currency plus a net worth in the base currency. Currencies without a usable rate are named in a warning and left out of the total instead of being guessed.
- Moving money between currencies: `thaler cli transfer --from Assets:Sparkasse --to Assets:Cash-USD --amount 100 --to-amount 108.50`. It is booked through `Equity:Conversions` so each currency balances on its own, and the effective rate is printed.

```sh
./thaler cli account add Assets:Cash-USD --currency USD
./thaler cli account add Assets:Cash-MXN --currency MXN
./thaler cli rate set USD EUR 0.92
./thaler cli rate set MXN EUR 0.05
./thaler cli currency set USD
./thaler cli balance
```

## Commands

Run without arguments, `thaler` opens the terminal UI (see above). Everything else lives under `thaler cli`; run `thaler cli --help` for the list. The interface needs a terminal, so scripts and cron jobs always use `thaler cli`.

| Command | Purpose |
| --- | --- |
| `thaler cli account add NAME -c EUR` / `thaler cli account list` | chart of accounts; first segment is the type (`Assets:`, `Liabilities:`, `Income:`, `Expenses:`, `Equity:`) |
| `thaler cli account rename OLD NEW` | give an Assets or Liabilities account a new name; its transactions, schedules and minimum stay with it |
| `thaler cli account close ACCOUNT` / `thaler cli account reopen ACCOUNT` | set an empty account aside, keeping its history, or take it back (see below) |
| `thaler cli account balance ACCOUNT AMOUNT [--as-of DATE]` | make the account hold what your bank shows, via an opening balance |
| `thaler cli add -a ACCOUNT --amount=-12.50 -t CATEGORY -p PAYEE -d DATE` | one income or expense |
| `thaler cli split ID --line CATEGORY[=AMOUNT]... [--amount N] [--date D] [--payee P] [--memo T]` | divide a transaction between categories, or change how a split is divided: the lines given replace all of them, one may leave out its share to take the rest, and they must add up to the amount or nothing changes; one line makes it an ordinary transaction again |
| `thaler cli transfer --from A --to B --amount N [--to-amount M]` | between your own accounts, also across currencies |
| `thaler cli transfer edit ID [--from A] [--to B] [--amount N] [--to-amount M] [--date D] [--in-date D] [--memo T]` / `transfer delete ID [--yes]` | change or delete both halves of a transfer together, given either half's number |
| `thaler cli transfer link A B` / `transfer unlink ID` | make two stored transactions the halves of a transfer, or two ordinary (uncategorized) ones again |
| `thaler cli import FILE -a ACCOUNT [--profile P] [--dry-run]` | import a bank export: CSV, OFX or QIF; the profile is found from the file (`auto`, the default) unless `--profile` names one (`sparkasse`, `ofx`, `qif` or one of yours) |
| `thaler cli list [-a ACCOUNT] [--from D] [--to D] [-n 30]` | transactions, newest last |
| `thaler cli export [DEST] [-a ACCOUNT] [--from D] [--to D]` | the transactions as CSV for a spreadsheet, oldest first, a line for each posting (id, date, payee, description, account, amount, currency; English column names, amounts as decimals with a point); to standard output, or to a new file readable by you alone that is never overwritten |
| `thaler cli recategorize [--dry-run]` | apply the config.toml rules to transactions still uncategorized |
| `thaler cli category set ID CATEGORY` | move one transaction to another category (created if new) |
| `thaler cli balance [--as-of D] [--all]` | balances and net worth |
| `thaler cli budget [-m YYYY-MM]` / `thaler cli budget set CATEGORY AMOUNT [-m M]` / `thaler cli budget clear CATEGORY [-m M]` | a month's spending against its targets (spent, target, carried in, left) a second table with the groups of categories added up (see Category groups) and, when income is planned, the income against its plan and what is unassigned; setting or clearing a category's target (an Income category's is the income planned); the month defaults to this one, amounts are in the base currency |

| `thaler cli forecast [--until D]` | the balance of each account today and after each day a schedule moves it |
| `thaler cli account minimum [ACCOUNT [AMOUNT] \| --amount N \| --clear]` | the lowest an Assets account should fall; `forecast` warns about the day it would |
| `thaler cli schedule` / `add NAME --unit U -a A --amount N [--to ACCOUNT] [--tolerance P] [--end D]` / `edit ID` / `delete ID` / `pause ID` / `resume ID` / `due [--until D]` / `confirm ID DATE [--amount N] [--to-amount N]` / `skip ID DATE` | recurring transactions: define them, list the dates that are due, and confirm (optionally for another amount) or skip each; nothing is booked without a confirm |

| `thaler cli backup [DEST] [--encrypt \| --passphrase-file F]` | consistent snapshot via `VACUUM INTO`, checked after it is written; **not encrypted** unless `--encrypt` (asks for a passphrase twice) or `--passphrase-file` (first line of a file, for scripts) is given, which writes an age file ending in `.age`; also `S` in the interface |

Write negative amounts as `--amount=-12.50`. Amounts accept `12.50`, `12,50` and `1.234,56`; ambiguous input such as `1,234` is rejected rather than guessed.

**For scripts: `--json`.** Every listing (`account list`, `account minimum`, `list`, `balance`, `budget`, `rate list`, `schedule list`, `schedule due`, `forecast`, `prune`, and the four `report`s) takes `--json`, which prints one JSON document instead of the table and nothing else (what a table says in a warning, such as a currency with no exchange rate, is in the data as a `missing` list; `prune --json` only lists, it refuses `--yes`). The document is what the service answered, written the same way everywhere: objects have `snake_case` keys in a fixed order (`spent_total`, `schedule_id`), lists are `[]` when empty and never `null`, an amount is `{"amount": "-12.50", "currency": "EUR"}` with the amount as text with a point (never a number, so no digit is lost), days are `YYYY-MM-DD`, months `YYYY-MM`, moments RFC 3339 in UTC, and an exchange rate is its exact decimal as text. `thaler cli export` writes transactions as CSV.

## Layout

```
cmd/thaler/           cobra commands (thin: parse flags, call core.Service, print) and wiring
internal/ledger/      Money, account naming, double-entry validation, FX rates   (stdlib only)
internal/importer/    CSV profiles, OFX and QIF, encoding and delimiter detection, dedupe keys, rules (stdlib only)
internal/core/        the application layer, see below
internal/config/      config.toml loading and default paths
internal/i18n/        the messages in English, Spanish and German (locales/*.json) and the language lookup
internal/tui/         Bubble Tea interface: panel layer, lists, fuzzy search, category picker, detail pane
```

`internal/core` is the only code that touches the database. The TUI and the CLI depend on its `Service` interface and nothing else, so a client for a remote server can replace the local SQLite backend later without changing them.

```
core/api.go           Service interface and the types that cross it
core/service.go       Local, the SQLite-backed Service: all rules (validation, import, reports)
core/repository.go    Local's SQL; unexported, so nothing outside core can bypass the rules
core/migrations.go    schema versioning
```

The schema lives in `internal/core/dbmigrations/`, applied by [golang-migrate](https://github.com/golang-migrate/migrate). Add `YYYYMMDDHHMMSS_name.up.sql` files for changes (the first three are dated `YYYYMMDD`, which sorts before any timestamp) and register the number in `migrationScriptTimestamps` in `internal/core/migrations_test.go`. The `schema_migrations` table holds the version of the last migration applied. A database that holds data is copied to `backups/pre-migration/` first; if a migration fails nothing is changed.

## Decisions worth knowing

- **No sqlc (yet).** Queries are plain SQL in `core/repository.go`, so moving to sqlc later is mechanical. Migrations are plain `.up.sql` files run by golang-migrate; there are no down migrations, the copy made before an upgrade is how to go back.
- **One database connection.** Fine for a single-user CLI. The TUI calls the service directly from its update loop (milliseconds on a local file); a network backend would need those calls moved into background commands, and this pool setting revisited.
- **Recategorizing re-books the category leg only.** A transaction's category is its single Income/Expenses/Equity posting; the amount, date and your own account never change. Transactions with no such posting or several (transfers, FX conversions) are refused.
- **Backups are plain SQLite files unless you encrypt them.** Encryption is by passphrase only (age with scrypt); there are no key files or public-key recipients yet, so an unattended encrypted backup needs the passphrase in a file (`--passphrase-file`). The live database itself is not encrypted: use full-disk encryption for that.
- **Rows have a uuid and a version, accounts have an owner.** Integer ids stay what the code uses; the uuid is the identity that survives export, restore and sync. `version` goes up on every edit so a stale client can be refused later. `accounts.owner_id` is NULL for shared accounts and a user for private ones. The `users` table exists but nothing reads these columns yet.
- **Dates are ISO strings**, money is `int64` minor units, exchange rates are exact rationals (`math/big`). No floats touch stored or reported amounts.

## Roadmap

[ROADMAP.md](ROADMAP.md) lists what is built and what is planned, as milestones, epics and stories with permanent IDs.
